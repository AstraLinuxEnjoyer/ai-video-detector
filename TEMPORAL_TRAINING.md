# Вторая модель: обучение и наблюдение

Новый запуск независим от старого `training.train_temporal` и от весов первой
модели. Не используй старую команду для этой инфраструктуры.

## Запуск

В PowerShell из `C:\Users\Ivan\Desktop\ai-video-detector`:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\train-temporal.ps1
```

Панель во время работы: `http://127.0.0.1:8766`. При занятом порте программа
выбирает следующий свободный и печатает точный адрес после `DASHBOARD`.
Никаких облачных сервисов или отправки видео наружу в панели нет.

Первый запуск начинает новое обучение R(2+1)D-18 из предобученных весов
Kinetics-400. Старые `models/temporal_best.pt` и пространственная модель не
изменяются. Следующий запуск той же команды продолжает новый эксперимент.
`--fresh` намеренно отсутствует: для нового эксперимента укажи другой `--run-dir`.

```powershell
# Только подготовить разбиение и декодировать первую эпоху + валидацию.
.\train-temporal.ps1 --prepare-only

# Открыть сохраненные результаты после окончания/остановки обучения.
.\train-temporal.ps1 -DashboardOnly

# Проверить лучшие temporal-веса на своих видео из test_videos/real и fake.
.\train-temporal.ps1 --evaluate-only

# Проверить зависимость ответов от порядка кадров без обучения.
.\train-temporal.ps1 -MotionAudit

# Отдельный эксперимент, не перезаписывающий стандартный.
.\train-temporal.ps1 --run-dir cache/temporal_v2/runs/experiment_02 --batch-size 2
```

Настройки существующего запуска зафиксированы. Изменение параметров требует
новой директории, чтобы сравнения, кэш и возобновление не меняли смысл посреди
эксперимента. `Ctrl+C` останавливает процесс. Возобновление идёт с последнего
сохранённого пакета; до 20 пакетов с момента сохранения могут быть повторены.
Не запускай два обучения одновременно: используется общий блокировочный файл.

## Что происходит

1. Читается снимок `cache/artifact_spatial/runs/hybrid_v2/splits.json`.
   Проверяются контрольная сумма и отсутствие пересечения ID/групп между
   train, val, test и OOD. Разделы не перераспределяются.
2. Для train выбираются 1000 разных видео на эпоху: 500 real и 500 fake.
   Баланс классов поддерживается в группах близкого разрешения и формата кадра.
   Внутри групп источники чередуются. UCF ограничен 20% реальной части.
   Это не означает равные глобальные квоты для каждого источника: совместимость
   разрешений и доступность данных ограничивают выбор. План каждой эпохи сохранён.
3. Из каждого train-видео выбираются два временных окна. Одно окно содержит
   16 кадров на равномерной сетке 16 FPS, то есть примерно секунду видео.
   Позиции случайные, но воспроизводимые и зависят от эпохи.
4. FFmpeg последовательно декодирует каждое окно одним процессом. Изображение
   приводится к центральному квадрату 128x128 с сохранением пропорций. На вход
   модели подаются 112x112. Это обрезает края, а не растягивает изображение.
   Полное исходное поле зрения в модели не сохраняется.
5. Одинаковые для всего клипа crop, flip, яркость, изменение размера и JPEG
   применяются без искусственного мерцания между кадрами. Одинаковое распределение
   преобразований используется для обоих классов.
   Дополнительно кадры удерживаются группами по 1, 2 или 4 с одним и тем же
   распределением для real/fake. Это мешает использовать низкий FPS как однозначную
   метку fake. Статичные сцены и низкий FPS сами по себе не означают генерацию.
6. R(2+1)D-18 вычисляет один logit на клип. BCE с небольшим сглаживанием меток
   сравнивает его с правильным ответом. Градиенты обновляют backbone и последний
   классификатор с разными скоростями обучения. Running statistics BatchNorm
   заморожены из-за маленьких коррелированных пакетов, обучаемые параметры остаются.
7. После эпохи проверяются фиксированные 800 видео, по три окна на видео.
   Итог видео: среднее оценок клипов, порог 0.5. Отдельно выполняется stress-проверка
   с уменьшением изображения, JPEG и удержанием каждого четвёртого кадра.
   Это не полное перекодирование видеопотока. В отчётах есть отдельные группы по
   исходному FPS; эти меры не гарантируют полного устранения FPS-подсказки.
8. Лучшие веса выбираются по среднему качеству источников внутри классов,
   усреднённому между clean и stress. Группы меньше 10 примеров исключены только
   из критерия выбора, но присутствуют в отчёте. Пять эпох без улучшения останавливают
   обучение; максимум 12 эпох. Затем лучшие веса проверяются на test и OOD.

За эпоху получаются 2000 обучающих клипов, 32000 предъявлений кадров и 500
пакетов по четыре клипа. Это не 32000 независимых обучающих видео.

## Откуда данные и ограничения

Используются уже доступные локальные файлы из зафиксированного каталога первой
модели, в том числе ранее загруженные удалённые видео. Новые датасеты автоматически
не скачиваются и не добавляются. Веса Kinetics могут скачаться при первом запуске,
если их нет в кэше PyTorch; на текущем компьютере они уже есть.

Последовательности DAVIS по умолчанию исключены явно: в нашем снимке неизвестна
их временная частота. При подтверждённой частоте можно создать новый эксперимент
с `--sequence-fps N`. Это значение применяется ко всем image_sequence в снимке;
не следует придумывать N. Первая модель продолжает использовать DAVIS независимо.

Известный повреждённый train-файл исключён согласно аудиту первой модели.
Все исключения и недоступные для matching группы отражены в `data_audit.json`.
Валидационные видео не заменяются другими. Любая новая ошибка чтения останавливает
процесс с конкретным ID/путём в `data_errors.jsonl`. Это сделано намеренно:
нельзя получать высокую accuracy путём незаметного исчезновения трудных примеров.
Слишком короткое видео (меньше секунды при стандартных настройках) в train/val
вызывает явную ошибку, а не padding. В итоговых test/OOD и ручной внешней проверке
оно получает явный отказ от классификации `clip_too_short`: ID, путь, источник,
длительность и требуемая длина сохраняются в `*_decode.json` и отчёте `coverage`.
Другой ролик не подставляется; метрики рассчитаны только по классифицированным
видео. Отдельно указаны исходное число запрошенных видео, покрытие по классам
и источникам, а также границы accuracy на всей исходной выборке: все отказы
считаются ошибками / правильными ответами. Это не доверительный интервал.
Другие ошибки чтения по-прежнему останавливают запуск. Если обучение уже завершено,
повторный запуск той же команды заканчивает тесты, не обновляя веса.
При неполном чтении окна возможны два повтора того же видео на 0.25/0.5 секунды
раньше. Фактическое время и причина сохраняются в `recovered_seeks` отчёта
декодирования; другой ролик не подставляется. Если повторы не помогли, запуск
останавливается.

Приведение FPS не устраняет все особенности источника. Низкий исходный FPS
может приводить к повторным кадрам. В `*_decode.json` записываются количество
таких роликов и клипов с одинаковыми соседними кадрами. Статичная реальная сцена
тоже может иметь одинаковые кадры; это не автоматический признак подделки.

Кэш клипов ограничен 12 GiB, свободный резерв диска 10 GiB. После завершения
эпохи удаляются только её декодированные train-клипы из собственного кэша;
исходные видео не меняются. Валидация и итоговый тест кэшируются отдельно.
Проверяется размер/время изменения исходников. Это не повторный полный SHA-аудит
каждого файла и не исчерпывающий поиск перцептивных дубликатов.

## Панель

- **Вход и решение:** декодированный клип, фактический преобразованный вход,
  все кадры по порядку, правильная метка, ответ до обновления на этом пакете,
  текущая ошибка, уникальные видео и скорость. Пример обновляется каждые 20 пакетов.
- **Качество:** train/clean/stress по эпохам, false positive rate, recall fake,
  ошибки по источникам, лучшая эпоха и итоговые test/OOD. Не смешивай clip accuracy
  с video accuracy.
- **Карты и время:** четыре фиксированных валидационных примера из обоих классов
  до обучения и после каждой эпохи. Обычный клип, Grad-CAM для предсказанного класса,
  ответы на перемешанный порядок, повтор кадра и закрытые временные участки.
  В меню эпох доступны исходный снимок и сохранённые снимки предыдущих эпох.
- **Веса и система:** измеренное изменение параметров первого, промежуточного,
  последнего блоков и классификатора, распределение выборки весов, норма градиента,
  скорость обучения, CPU, RAM, GPU, VRAM, время ожидания и вычислений.

CPU/RAM/GPU относятся к компьютеру/адаптеру целиком, а пик PyTorch к этому процессу.
Скорость в панели измеряет последний пакет без затрат на сохранение, визуализацию
и предварительное декодирование; она не равна средней скорости всего запуска.
Счётчики отсутствуют, если системный API недоступен; ноль не подставляется.
Чтение и запись `live.json` согласованы между процессами. При временной блокировке
файла Windows обновление панели откладывается с предупреждением `TELEMETRY`,
а обучение продолжается. После освобождения файла публикуется актуальное состояние.
Эта политика не применяется к чекпоинтам: ошибки их сохранения не скрываются.

Отдельные веса не имеют названий вроде «плохая рука». В панели измерения изменения
весов служат проверкой, что оптимизатор действительно работает. Grad-CAM имеет
грубое исходное разрешение, интерполируется и нормализуется для каждого клипа.
Яркость между клипами напрямую сравнивать нельзя. Нулевая карта явно отмечена.
Изменение оценки после перемешивания не доказывает обнаружение генерации:
перемешивание само создаёт необычный вход. Эти четыре примера диагностические,
а не статистический тест временной способности всей модели.

## Как сеть учится отличать движение

Модель получает только пиксели клипа. Правильная метка используется в функции
ошибки, но не передаётся как вход классификатору. Имя папки/источник также не
поступают в сеть. Программа знает метки, чтобы оценивать ошибки и строить выборки.

Пространственные свёртки выделяют структуры внутри кадров. Временные свёртки
сравнивают соседние положения признаков во времени. Следующие блоки объединяют
локальные изменения в более сложные пространственно-временные сочетания.
Последний слой превращает накопленные признаки в один logit, sigmoid в оценку fake.

У сети нет врождённого определения нормальной физики. Представим fake-клип,
которому она дала score=0.2: функция ошибки велика и градиент меняет веса в сторону
более высокого ответа на связанные признаки. На real-клипах этот сигнал направлен
в другую сторону. Повторение на разнообразных примерах позволяет найти регулярности,
но не гарантирует, что ими станут именно дефекты движения. Регулярностью может
оказаться фон, кодек, FPS, разрешение, лицо или характер съёмки.

Поэтому инфраструктура сочетает баланс данных, общие преобразования, отдельную
проверку источников, stress-тест и временные вмешательства. Это снижает некоторые
риски и делает ошибки видимыми, но не превращает обычную классификацию в модель
физического мира. Тепловая карта не позволяет честно написать «она поняла, что
палец движется неправильно». Такого словесного рассуждения у этой сети нет.

## Где результаты

Основной каталог: `cache/temporal_v2/runs/r2plus1d_v1/`.

| Файл | Содержимое |
|---|---|
| `training.log` | Текстовый лог, одновременно в консоли |
| `config.json`, `splits.json`, `data_audit.json` | Зафиксированная настройка и аудит данных |
| `checkpoint.pt` | Веса, оптимизатор, scheduler, AMP, RNG, план, смещение и история покрытия |
| `best.pt`, `best.json` | Лучшие веса и причина выбора |
| `last.pt` | Последняя полностью завершённая эпоха |
| `epoch_NNN.json`, `epoch_NNN_plan.json` | Метрики и ID выбранных видео |
| `epoch_NNN_clean.csv`, `epoch_NNN_stress.csv` | Ответ на каждое валидационное видео |
| `performance.jsonl` | Измерения обучения и системы по пакетам |
| `explanations_NNN.json`, `previews/` | Контрольные вмешательства, GIF и карты |
| `coverage.json` | Уникальные train-ID завершённых эпох |
| `numerics.jsonl`, `data_errors.jsonl` | Восстановленные численные ошибки и проблемы данных, если были |
| `final_report.json`, `test_predictions.csv`, `ood_predictions.csv` | Итоговая проверка лучших весов |
| `test_report.json`, `ood_report.json` | Отчёт каждого теста сразу после его завершения, включая coverage и явные отказы |

Метрики из технического запуска `cache/temporal_v2/smoke/` нельзя использовать
как оценку качества. Он проверяет чтение реальных файлов, CUDA, обновление весов,
сохранение, вычисление метрик и визуализации на очень маленькой выборке.

## Вместе с первой моделью

Этот этап ещё не объединяет модели в работающий ансамбль и не меняет backend.
ID видео и разбиения совместимы с первой моделью. После обучения сравниваем ответы
на общих ID, долю совпадающих ошибок и качество объединения. Веса ансамбля и порог
подбираем на валидации, затем фиксируем до тестирования. Уже изученные тесты не
являются новым слепым бенчмарком. OOD только из fake не измеряет false positive rate.
Произвольную короткую подделанную вставку три окна могут пропустить: для такой
задачи нужен более плотный проход и отдельная проверка частичных манипуляций.
