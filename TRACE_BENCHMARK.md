# Независимая проверка двух моделей TRACE

Тест использует те же веса и тот же вход, что и действующая демонстрация:
`hybrid-v2` по кадрам и `temporal-motion-v1` по оптическому потоку. Он не
обучает модели, не изменяет кэш обучения и не включает спектральную модель.
Выбираются веса демо, если они установлены; иначе используются `best.pt`
этих двух запусков. Точные хэши записываются в отчёт.

## Куда положить видео

Создай папки внутри проекта. Первая подпапка под `real` или `fake` станет
названием источника в отчёте:

```text
test_videos/benchmark/
  real/iphone/clip01.mov
  real/ordinary_edits/clip02.mp4
  fake/unseen_generator/clip03.mp4
  fake/local_edit/clip04.mp4
```

Используй ролики, не участвовавшие в разработке, и проверь их происхождение.
Например, stock-видео, снятое камерой, не становится fake оттого, что его
скачали с сайта. Не добавляй несколько пережатых копий одного видео как
разные примеры. Точное совпадение файла с известными разделами проверяется
по SHA256, если локальные снимки соответствуют используемым весам.
Переупакованные копии, совпадения сцен и новые версии одного оригинала
этой проверкой не обнаруживаются. Наличие аудио на оценку не влияет.
Те же ограничения демо: до 120 секунд; слишком короткие ролики или ролики
с исходным FPS ниже входной частоты не оцениваются моделью движения.

### Проверка времени вмешательства

Чтобы измерить точность дорожки, добавь `test_videos/benchmark/segments.json`:

```json
{
  "fake/local_edit/clip04.mp4": [[3.5, 6.0], [8.0, 10.2]]
}
```

Это начало и конец каждого изменённого интервала в секундах. Разметка
нужна только для роликов с известными интервалами. Неразмеченные fake
входят в оценку классификации, но не в метрики таймлайна. Для real
измеряется, сколько чистых секунд было ошибочно выделено.

## Запуск

Из корня проекта:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\evaluate-trace.ps1
```

Опции: `--device cuda` для ускорения инференса, `--no-reencode` для проверки
только исходников, `--input <папка>` для отдельной выборки. Декодирование
и оптический поток остаются на CPU. Пережатие H.264 CRF 30 выполняется
во временной папке, по одному SDR-видео с чётными размерами за раз;
исходники не перезаписываются. Для HDR или неподдержанного файла причина
попадёт в отчёт. Это один контроль пережатия, не имитация всех соцсетей.

## Как принять решение

Результаты находятся в `reports/trace_benchmark_<время>/`: `evaluation.log`,
`report.json`, `predictions.csv` и `predictions.json` с оценками кадров,
клипов и выделенными интервалами.

- Сравни `clean.same_videos` для spatial, temporal и суммы 70/30. Это одна
  и та же группа роликов, где обе модели дали полную оценку. `clean.all`
  показывает реальное покрытие каждой модели. Пропуск не считается REAL.
- `demo_alert` воспроизводит старое правило: хватало одного кадра или клипа.
  `policy_alert` проверяет текущий `trace-evidence-v3`. Полная разбивка на
  `suspected`, `uncertain`, `no_signals` есть в `policy_verdicts`. Нулевой
  флаг в бинарной сводке не означает REAL: туда входят и неопределённые
  результаты. Балл 70/30 измеряется отдельно. Пороги не подгоняются по тесту.
- Смотри на ложные тревоги и пропуски по источникам, AUROC для непрерывных
  оценок, парное падение после пережатия и совпадение с разметкой времени.
  `intervals_half_covered` считает интервалы, покрытые минимум наполовину;
  длинная подсветка всего ролика также даст высокий охват, поэтому смотри
  одновременно на `predicted_seconds`, `overlap_seconds` и ложную подсветку
  на реальных видео. Это оценка времени, не попиксельная локализация.
- Если движение добавляет правильные срабатывания без лишних тревог и
  дорожка попадает в интервалы, двигайся к демонстрации. Если ошибки
  устойчиво группируются по сценарию (склейки, новые генераторы, пережатие
  или локальная подмена), сначала дообучай ветку, которая там ошибается.
  После изменений проверь результат на новом, ещё не просмотренном тесте.
